# Purchase service handoff — WEB06 / WEB07

Prepared October 15, 2026. **Proposed integration contract; service work is not implemented.**
The local website preparation is separate from COM01, COM02 and APP01 acceptance.
Josh authorized placeholders and preparatory work while the purchase process is finalized.
No domain, provider account, secret, policy approval or successful transaction is assumed.
The desktop repository was inspected without modification.

## Website boundary already implemented

- Home Pricing links to `/purchases?plan=free|monthly|lifetime#plan`. Only a single recognized plan selects a panel; absent, unknown or repeated selections show Free. Selection carries no price, customer, entitlement or payment authority. It never starts checkout automatically.
- `src/content/commerce.ts` defaults to unavailable. In-app offers require an accepted release matching `releaseVersion`, public-policy readiness including purchase-service privacy, a live HTTPS service origin, and owner references for commercial approval, direct-route acceptance and desktop compatibility. These records are references for human review, not authenticated evidence.
- Standalone links additionally require the `website-purchase-v1` contract and its acceptance record. The only destinations generated are `<approved service origin>/buy/monthly` and `/buy/lifetime`; no user-supplied return URL, price ID, customer ID or credential is forwarded. Links suppress the referrer. GET must show the offer without creating a transaction.
- Missing website acceptance falls back to the separately accepted in-app route. Missing direct acceptance disables both paid routes. Downloads have their own record and remain independent. Review mode never renders a live checkout link. No sandbox flag, query parameter or browser-storage setting activates commerce.
- Safe marketing return/help destinations are `/help#payment-help`, `/help#restore`, `/downloads` and `/purchases`. Return links must use the eventual approved marketing origin and carry no credentials, codes, payment identifiers or claimed success. This frontend never interprets a success query, receives a recovery code, checks payment or issues access.
- Existing customers can read restore/manage instructions even while new sales are unavailable. The website does not determine whether their service account or cached desktop access works.

## Current desktop/service contract

References below are relative to `../collie-writer`.

`AccessPanel.tsx`, `DirectAccessPanel.tsx` and `WorkspaceNavigation.tsx` already provide **Settings → Collie access**, Monthly/Lifetime, **Restore purchase…**, **Continue in browser**, **Check completion**, **Refresh purchase access** and **Manage subscription…**. A second pricing modal is unnecessary for this website preparation. Prices match $9.99 USD/month and $199 USD once. The app configuration is null, issuer keys empty and `services/entitlements/policy.mjs` disables checkout; these source controls are not readiness evidence.

| Existing service operation                              | Meaning to preserve                                                                                                                                                                                                |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Native `POST /v1/sessions`                              | Exact app-owned session/credential hashes; refuses browser Origin headers; 20-minute expiry. Do not call from the marketing site or weaken its origin check.                                                       |
| `/connect` with app-supplied fragment                   | Browser credential is separate from app claim/connection credentials; fragment is removed before Paddle loads. No account or device impersonation in the website.                                                  |
| `POST /v1/browser/checkout`                             | Service owns plan/catalog; keeps the transaction ID and refuses silent retries after uncertain creation.                                                                                                           |
| `POST /v1/browser/recovery`                             | Reconciles the canonical completed transaction, then currently replaces the customer's recovery hash on **each** successful call. This needs deliberate display/replacement handling before commercial acceptance. |
| `POST /v1/browser/restore` → native `/v1/session/claim` | Recovery code proves purchase authority; desktop claim returns signed grants and connection authority. `{ready:false}` never unlocks access.                                                                       |
| Native `/v1/access`, `/v1/manage`, `/v1/disconnect`     | Explicit refresh, authenticated provider portal and connection removal. Disconnect does not cancel billing or remove projects. Restore remains independent of new-sale approval.                                   |

`server.mjs`, `paddle.mjs`, `reconcile.mjs`, `public/connect.js` and `store.mjs` are the source owners. The service README's historical `docs/formats/direct-commerce-v1.md` reference is absent; this document does not claim to replace an existing implemented wire contract.

## COM02 proposed service-owned flow

Only the fixed plan-entry paths above are assumed by website code. The following service-internal interface is a concrete proposal for the separate implementation, **not existing endpoints or Paddle API definitions**. COM02 can revise its internals without adding a marketing API client.

| Proposed service operation                        | Request and response meaning                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /buy/monthly` or `/buy/lifetime`             | Show exactly that plan, real seller/terms/privacy/support and final-checkout notice. May establish a bounded secure browser/CSRF context; must not create a purchase on navigation, prefetch or reload.                                                                                                                                                                           |
| `POST /v1/website/purchases`                      | Explicit service-page action with an allowlisted plan and server-issued intent/CSRF token. Deduplicate the intent before creating the provider transaction. Return the same attempt's checkout presentation, or a pending/unknown outcome; never create another transaction as an automatic retry. Reject arbitrary catalog/amount/currency/quantity/environment/redirect inputs. |
| `GET /buy/complete` and `POST /v1/website/status` | Authenticate the same bounded browser context; reconcile only its retained attempt. GET displays status, POST rechecks. A provider browser callback is a prompt to reconcile, never fulfillment evidence.                                                                                                                                                                         |
| `POST /v1/website/recovery`                       | Only a confirmed paid attempt with valid completion authority may reveal recovery material. Separate explicit replacement from status/reload; never silently rotate a code already shown.                                                                                                                                                                                         |

Normal confirmed presentation: **Save your recovery code → Install/open Collie Writer → Restore purchase**. Include the approved Downloads and restore-help links, plus an installed-user route. New visitor checkout must not require a desktop installation or create a marketing account.

| Service state                           | Customer presentation and allowed next action                                                                                                                               |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Awaiting payment / confirmation pending | Check the **same** attempt; no code or paid-access claim.                                                                                                                   |
| Creation outcome unknown                | Preserve the durable intent; reconcile or use verified support. No automatic retry charge or new attempt.                                                                   |
| Confirmed                               | Canonical provider transaction, approved catalog/amount/currency/quantity/edition and customer association verified; durable fulfillment committed before recovery display. |
| Canceled / failed                       | Only after the known outcome is established, offer a deliberate retry or return to free writing. Closing an overlay alone does not establish failure.                       |
| Session expired / lost                  | No disclosure without authority. Saved code uses normal app restore; otherwise verified purchase support. Expiry does not delete paid records.                              |
| Service unavailable                     | Explain temporary unavailability, preserve the attempt and cached rights, retain help/free-download paths. No paid success or silent new charge.                            |

Use separate random browser completion authority with secure, HttpOnly, SameSite cookies and explicit CSRF/same-origin enforcement. Define and disclose the exact lifetime during COM02. Keep responses `no-store`, non-indexable and referrer-restricted; omit all recovery/session secrets from URLs, logs and third-party scripts. Preserve existing native endpoint origin protections. Do not enable cross-origin browser APIs for the marketing frontend.

Persist attempt, intent, transaction and customer association before fulfillment. Keep paid history independent of short-lived sessions. Choose a bounded recovery-display design explicitly: hashed long-term recovery storage must remain; if redisplay requires encrypted temporary material, define its access, encryption and deletion lifetime. After display authority expires, use explicit verified replacement/support rather than retaining plaintext indefinitely or promising email delivery. Additional purchases for an existing customer must use verified recovery/account authority, never email matching alone; preserve the connected app purchase path.

## Migration and desktop compatibility

`store.mjs` creates schema 1 only for an empty store and refuses unknown schema versions. COM02 needs an explicit migration that preserves `purchases`, monotonic revisions, recovery hashes, credentials, active native sessions, webhook receipts and issuer identity/keys. Add durable web attempts/completion state without resetting the database. Preserve current per-customer reconciliation and webhook deduplication. Retain enough association for late confirmation after browser closure; resolve unknown creation without assuming provider idempotency support. Operator backup/restore and deployment remain separate tasks; never copy an active SQLite main file alone or resume from older revision high-water marks without reconciliation.

APP01 must establish that the accepted direct build trusts the real issuer/origin, can restore a website-created purchase through the unchanged code path, checks completion, refreshes changes and opens authenticated subscription management. No custom URL scheme, automatic app activation or project upload is needed. Signed installers, secure credential storage and observations on each offered platform are still missing.

## Current provider references and integration gaps

Official documentation consulted October 15, 2026. These are source/documentation findings, not provider approval or successful API observations.

- [Domain review](https://www.paddle.com/help/start/account-verification/what-is-domain-verification): real product/pricing and accessible terms, refund and privacy content are needed for live review; checkout subdomains need their own approval. Current placeholders cannot establish that approval.
- [Default payment link](https://developer.paddle.com/build/transactions/default-payment-link/): an approved page with Paddle.js handles `_ptxn` payment links, including subscription payment-method updates. **Actual source gap:** the service rejects every query string, and `/connect` needs the app's fragment. COM01 must add a narrow provider payment-link path/handling without relaxing all request validation or treating `_ptxn` as recovery authority. Do not point the provider default link at this static marketing page.
- [Pass a transaction to checkout](https://developer.paddle.com/build/transactions/pass-transaction-checkout/) and [checkout settings](https://developer.paddle.com/build/checkout/set-up-checkout-default-settings/): service-created transaction IDs fit the existing route. Keep client-side Paddle initialization on the service origin and server API keys private. Reconcile current provider settings/CSP with the permanent no-ads requirement before enabling.
- [Checkout completion callback](https://developer.paddle.com/paddle-js/events/checkout-completed/) and [transaction completion](https://developer.paddle.com/webhooks/transactions/transaction-completed/): a browser event may precede captured/processed completion. Preserve the service's canonical `completed` check and signed-grant authority.
- [Webhook delivery](https://developer.paddle.com/webhooks/about/how-webhooks-work/) and [signature verification](https://developer.paddle.com/webhooks/about/signature-verification/): events can repeat or arrive out of order. Preserve exact-body verification, durable event-ID deduplication and canonical reconciliation; do not grant from the marketing redirect or unverified callback.
- [Products/prices](https://developer.paddle.com/build/products/create-products-prices/): tax mode and price overrides are catalog concerns. Current code checks the two USD prices, interval/no trial and no overrides at creation. Owner review must confirm catalog product/edition, totals, taxes and recurring terms across checkout and receipts.
- [Supported countries](https://www.paddle.com/help/start/intro-to-paddle/which-countries-are-supported-by-paddle) and [Checkout.open](https://developer.paddle.com/paddle-js/methods/paddle-checkout-open/): provider-supported geography or prefilling a country does **not** establish Collie's US-only sales restriction. The adapter README explicitly says it does not restrict geography. COM01 must settle provider/account enforcement and its acceptance before claiming US-only live sales; no guessed `allowedCountries` parameter is introduced here.
- [Customer portal](https://developer.paddle.com/build/customers/integrate-customer-portal/): generate customer-specific temporary sessions when requested. Preserve authenticated app/service management; no shared/static portal URL or unauthenticated customer-ID lookup.
- [Buyer refund guidance](https://www.paddle.com/help/manage/your-customers/buyers-refunds): refund requests and subscription assistance involve the provider's buyer-support process. Final seller/provider wording must be approved together; the site promises no invented refund window.
- [Sandbox](https://developer.paddle.com/sdks/sandbox/): keep sandbox/live accounts, credentials, catalog, issuer keys and data distinct. This marketing site's live action gate cannot be enabled with a sandbox record. Any sandbox purchase review belongs on a separately authorized isolated service/build, not a hidden website mode.

COM01 owns the default payment-link compatibility, merchant/catalog/geography/policy setup and safe repeated recovery handling; COM02 owns the new browser initiation, durable web fulfillment and migration. Neither is completed by this handoff. No service or desktop files were changed, no API requests/transactions were sent, and no accounts, hosts or secrets were provisioned.
